# AX.25 on XRouter

This page describes how XRouter implements the AX.25 data link layer: connected-mode
sessions, the modulo-8 and modulo-128 sequence-numbering schemes, selective reject,
digipeating and the heard-stations list. It is written for a sysop who already knows what
AX.25 *is* and wants to know how XRouter behaves and where to tune it. If you need the
fundamentals first, frames, addresses, SSIDs, the difference between UI and connected
frames, start with the primer, **[AX.25: the data link](../basics/ax25.md)**.

XRouter has its **own** AX.25 stack built into the program. It does not use the Linux
kernel's AX.25 subsystem; it speaks KISS, serial and various IP transports directly. That
independence is deliberate and is one reason XRouter keeps working as the kernel AX.25 code
ages, see [The TCP/IP stack](tcpip.md) for the same story on the IP side.

## Connected-mode sessions

Most user traffic through a node is **connected mode** (AX.25 "I" frames): a reliable,
sequenced, acknowledged link between two stations. XRouter maintains a level-2 link for
each such connection, on a per-port basis, in XRouter a *port* is normally one radio
frequency, and all AX.25 operation is port-based. You can see the live level-2 links at any
time with the `AX[routes]` command (sysop) and the user-visible `L[inks]` command.

The behaviour of those links is governed by the standard AX.25 timers and counters, all of
which XRouter exposes as per-port settings:

| Setting | Controls | Typical default |
| --- | --- | --- |
| `MAXFRAME` | Max unacknowledged I-frames outstanding (the window) | `3` |
| `PACLEN` | Max bytes of data per frame | `120` |
| `FRACK` | T1, the frame-acknowledgement timeout (ms) | `7000` |
| `RESPTIME` | Delayed-acknowledgement timer (ms) | `1500`–`2000` |
| `RETRIES` | Max connect / disconnect / resend attempts | `10` |
| `T3` | Link-check (keep-alive) timer (s) | `180` |

These are the knobs you adjust for channel conditions. On a slow 1200-baud RF channel the
defaults are sensible; on a fast wired or internet link you would lower `FRACK` and
`RESPTIME` substantially. Because they are per-port, a node with both a 1200-baud user port
and a fast backbone link can tune each independently. The full keyword list and where each
one is valid is on **[Ports](../configuration/ports.md)**.

!!! note "AX.25 behaviour is tuned per port"
    Almost everything on this page, window size, packet length, timers, digipeating,
    MHEARD, even whether NET/ROM runs at all, is set inside a `PORT…ENDPORT` block, with
    optional global defaults. There is no single "AX.25 mode" switch; you describe each
    radio frequency's link behaviour on its own port. See
    [Ports](../configuration/ports.md).

## Modulo-8 and modulo-128 (extended sequence numbers)

Classic AX.25 numbers frames modulo 8, which caps the send window at 7 unacknowledged
frames. On a fast or high-latency link that window empties before an acknowledgement
returns, and throughput stalls. AX.25 version 2.2 adds **modulo-128** ("extended")
sequence numbers, raising the ceiling to 127 outstanding frames.

In XRouter the scheme is chosen by the window size you ask for. Set the port's `MAXFRAME`
to **8 or more** and XRouter will attempt modulo-128 on that link; leave it at 7 or below
and the link stays modulo-8. The two ends negotiate at connect time, so a modulo-128-capable
port still talks happily to an older modulo-8-only station, it simply falls back.

You can also force an *outgoing* connection to use modulo-128 regardless of the port default
with the `CX` command (the modulo-128 counterpart of `C[onnect]`), which is handy for
testing a link.

!!! tip "Where extended mode actually helps"
    Modulo-128 only pays off when the link can keep many frames in flight, a fast modem, a
    9600-baud or faster channel, or an internet [AXIP/AXUDP](../interfaces/axip-axudp-axtcp.md)
    link with appreciable latency. On a plain 1200-baud channel a window of 3–4 frames is
    usually all the channel can carry, and modulo-8 is fine.

## Selective reject and resequencing

When a single frame in a window is lost, basic AX.25 recovers by going back and resending
from the missing frame onward, even though later frames may have arrived intact. XRouter
supports **selective reject (SREJ)**, asking the sender to retransmit only the specific
missing frame, and **resequencing** of frames that arrive out of order. On a marginal RF
path this avoids needlessly resending data the far end already holds, which is a real
throughput win when only the occasional frame is being lost rather than long bursts.

## Digipeating

XRouter is a fully featured digipeater as well as a node. At the AX.25 level it will repeat
frames addressed through it as a digipeater (up to the usual chain of relays), and it
handles both ordinary connected-mode digipeating and UI-frame digipeating. Digipeating is
configured per port through the `DIGIFLAG` bitmask, with related keywords such as
`DIGIPORT` to repeat onto a *different* port (cross-band or RF-to-internet digipeating). The
APRS-style "New-N" aliases (`UITRACE`/`WIDEn-n`, `UIFLOOD`) are part of the same machinery;
those are covered with the rest of APRS on
**[APRS digipeater and IGate](../subsystems/aprs-igate.md)**. For ordinary node operation
you rarely need to change `DIGIFLAG` from its default.

A separate, related facility is the **frame pipe** (`PIPE`/`PIPEFLAG`), which forwards
selected frames from one port to another, useful for funnelling a particular station or
service across ports. It is listed with the port keywords on
[Ports](../configuration/ports.md).

## MHEARD: the heard-stations list

Each port can keep an **MHEARD** list of recently heard callsigns, which is the first thing
most sysops check to confirm a port is actually receiving. Enable it and set its depth with
the per-port `MHEARD` keyword (0 disables it); `MHFLAGS` controls *what* gets recorded,
stations heard direct, stations heard via digipeaters, and the digipeaters themselves. Users
read it with `M[heard]`, and a sysop can clear it with `MHCLEAR`. The heard list is also
what feeds the node's view of who is active on a frequency, so it is worth leaving on for
any real RF port.

## How this differs from the beginner primer

The [basics AX.25 page](../basics/ax25.md) explains the protocol in the abstract, what a
frame looks like, why SSIDs exist, what "connected mode" means. This page is about
**XRouter's implementation choices**: that it carries its own stack, that modulo-128 is
gated on `MAXFRAME>7`, that SREJ and resequencing are available, and that every behaviour is
a per-port setting. When the two pages appear to overlap, the primer describes the standard
and this page describes what XRouter does with it.
